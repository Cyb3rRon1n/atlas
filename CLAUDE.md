# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
# Setup — use the [dev] extra, not requirements.txt (see Testing note below)
python -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"

# Run the CLI
atlas <command>            # e.g. atlas discover, atlas analyze, atlas doctor
python -m atlas.cli.main <command>   # equivalent, for running from source without reinstalling

# Tests (pytest, no config beyond auto-detected rootdir)
python -m pytest tests/
python -m pytest tests/test_discovery.py -v
python -m pytest tests/test_intelligence_providers.py::TestAnthropicProvider::test_refusal_raises_provider_error
python -m pytest tests/ --cov=atlas --cov-report=term-missing   # coverage, matches CI

# requirements.txt is a pip-freeze lockfile regenerated from the venv, not hand-edited,
# and is NOT used for install (see Testing note below):
pip install <new-package>
pip freeze > requirements.txt
```

There is no configured linter or formatter — nothing enforces style automatically. CI (`.github/workflows/ci.yml`) runs the test suite on Python 3.11/3.12 for every push/PR to `main`; it does not gate on a coverage threshold. **CI runs on `ubuntu-latest`, but this project's actual day-to-day development and real-infrastructure verification happens on Fedora** (this machine — `/etc/os-release` says Fedora Linux 44 Workstation, Python 3.14.6) — found while scoping second-distro verification, and it corrected a real inaccuracy: earlier docs claimed Ubuntu was "the platform this project actually develops and tests against," which was never true in this session. See the second-distro verification entry in the Architecture section below and the roadmap for what that means for Atlas's actual distro coverage.

**Testing note:** `requirements.txt` is a `pip freeze` dump that includes a self-referential editable install line (`-e git+ssh://...`) — this only works on a machine with SSH access to the repo, so CI (and any fresh clone) must install via `pip install -e ".[dev]"` against the checked-out tree, never `pip install -r requirements.txt`. Most tests rely on two `tests/conftest.py` fixtures rather than hitting real state: `isolated_cwd` (chdirs into a temp dir, since a real local `atlas.yaml` exists and `load_config()`/file-writing code reads/writes relative to cwd) and `temp_db` (points `KnowledgeStore`/`KnowledgeQueries` at a throwaway SQLite file instead of the real local `inventory/atlas.db` — done by monkeypatching the `engine` name in both `atlas.knowledge.store` and `atlas.knowledge.queries`, since each did `from atlas.database.engine import engine`, a local name binding). Docker- and hostname-resolution-dependent code (`atlas/docker/manager.py`, `atlas/discovery/network.py`) is mocked in tests rather than relying on ambient environment state, since GitHub-hosted runners have a live Docker daemon and CI network namespaces can't always resolve their own hostname.

## Architecture

**Runtime wiring.** `atlas.core.application.application` is a module-level singleton (`AtlasApplication`) constructed at import time; it owns an `AtlasRuntime` (`atlas/core/runtime.py`), which in turn owns:
- `AtlasContext` (`atlas/core/context.py`) — a plain dataclass bag (`config`, `inventory`, `docker`, `proxmox`, `services`, `health`) that subsystems write into.
- `AtlasEnvironmentContext` (`atlas/intelligence/context.py`) — the accumulated discovery snapshot (system/hardware/storage/network/services/containers/virtualization), updated via `.ingest_discovery(data)` after `atlas discover` and read back via `.summary()`.
- `EventBus` (`atlas/events/bus.py`) — a synchronous pub/sub bus; `subscribe("*", cb)` receives every event type.

CLI commands (`atlas/cli/main.py`) reach the singleton via `from atlas.core.application import application; runtime = application.runtime` rather than constructing their own runtime.

**Event flow.** Almost everything that produces data publishes an `AtlasEvent(event_type, source, payload)` on the bus (see `atlas.discovery.completed`, `atlas.plugin.loaded`, `atlas.analysis.completed`, `atlas.action.container_restarted`). `atlas/listeners/database.py`'s `DatabaseListener` subscribes to `"*"` and persists every event via `KnowledgeStore.save_event`; it's registered onto every `AtlasRuntime`'s event bus in `atlas/core/runtime.py`'s `__init__` (`DatabaseListener().register(self.events)`). **This registration was missing until it was added** — the listener class existed but nothing ever instantiated/registered it, so `atlas history` was silently non-functional (no published event was ever persisted; only the direct `save_environment()`/`save_analysis()` calls worked) for the entire life of the project up to that point. If event persistence ever looks broken again, check this wiring first. `atlas/listeners/logger.py`'s `EventLogger` (prints plugin-load events) is defined but still **not** registered anywhere — leave it that way unless you have a specific reason, since wiring it up changes visible CLI output for every existing command that publishes events. New features that produce meaningful state changes should publish an event rather than writing to the knowledge store directly from the CLI command, to keep that persistence path centralized.

**Approval-gated actions.** `atlas restart <name>` was the first command that mutates infrastructure instead of observing it; `atlas proxmox restart <vmid>` was the second (Proxmox guest instead of Docker container); `atlas stop <name>` (backed by `stop_container` in `atlas/docker/manager.py`) was the third — a genuinely different verb, not just another restart on a different resource type; `atlas resize <name>` (backed by `resize_container`) is the fourth — the first one that isn't a single fixed operation, taking `--cpus`/`--memory` instead. All four follow the same shape: the capability itself is a pure function returning a plain result dict (`{"success"/"found": bool, "error": str, ...}`, never raising the underlying library's exceptions to the caller — same style as `collect_containers()`); the CLI layer shows the current state and gates on `typer.confirm()` (default deny, no bypass flag) before calling it; the result is published as an event so it's logged via the same `DatabaseListener` path as everything else — no bespoke persistence code. The Proxmox token needs write/power-management permission beyond the read-only scope that's enough for `atlas proxmox scan` — see [Configuration](configuration.md#proxmox).

**Proxmox stop/resize parity.** `atlas proxmox stop <vmid>` and `atlas proxmox resize <vmid> --cpus/--memory` (`stop_guest()`/`resize_guest()` in `atlas/proxmox/manager.py`) close the gap between Docker's three actions and Proxmox's one — same pure-result-dict, never-raises shape as every other manager function, same `typer.confirm()` gate, same event-publish path (`atlas.action.guest_stopped`/`atlas.action.guest_resized`, sources `"ProxmoxStopAction"`/`"ProxmoxResizeAction"`, prefixed to disambiguate from the Docker `"StopAction"`/`"ResizeAction"` sources the same way `"ProxmoxRestartAction"` already was). Two real API distinctions, found by reading Proxmox's actual endpoints, not assumed: (1) Proxmox has no single call with Docker `container.stop()`'s built-in graceful-then-force behavior — `status.shutdown` (ACPI request, no automatic force-fallback if the guest doesn't respond) and `status.stop` (hard power-off) are separate endpoints. `stop_guest()` uses `shutdown` — matches what "stop" means in Docker's own default and most tooling — and the CLI's confirmation text says outright that this can stall on an unresponsive guest, rather than implying Docker-equivalent guaranteed termination. (2) Docker's `--cpus` maps to Proxmox's `cpulimit` (a float cap on host-core usage), **not** `cores`/`sockets` (CPU topology — how many vCPUs the guest OS sees, a completely different concept that generally needs guest-side hot-add support to take effect without a reboot). `--memory` maps straightforwardly to Proxmox's `memory` (MB) config field, reusing `docker.utils.parse_bytes()` (the same helper `resize_container` already uses) to accept the same `"512m"`/`"1g"` strings, converted to MB since Proxmox's API takes a plain integer with no unit parsing of its own — `atlas/proxmox/manager.py` didn't previously import `docker` at all; it now does, purely for this helper, no new dependency. **Verified against a real Proxmox VE host and the same real LXC test guest used for `restart` verification**: started the (normally stopped) guest, ran `atlas proxmox resize --cpus 0.5 --memory 256m` against it, and confirmed via a direct config read (`cpulimit: 0.5`, `memory: 256`) that both applied live to the running LXC, not just written to config for next boot — then ran `atlas proxmox stop` and confirmed via a status check that the guest genuinely stopped. The CLI prints an extra caveat for a `qemu`-type guest specifically (a resize may need hotplug enabled to apply without a restart, unlike LXC) — this has since been independently verified against a real QEMU VM (see below); don't claim it's unverified going forward.

**The QEMU hotplug caveat, verified against a real VM via Proxmox's own `pending` API — not guessed, and not just re-reading docs.** `/nodes/{node}/qemu/{vmid}/pending` returns each config key with a `value` (what the *running* instance actually has) and, only when a write hasn't taken effect yet, a separate `pending` field — Proxmox's own authoritative signal for "did this apply live or get queued." Test VM kept `kvm: 0` (software emulation) since this Proxmox host has no hardware virtualization available at all — irrelevant here, since only config-application behavior was under test, not guest performance. Three real findings: (1) `cpulimit` applies live to a running `qemu` guest regardless of hotplug, same as `lxc` — `pending.get()` returned a bare `value`, no split, confirming the "host-side cgroup cap" assumption for both guest types now, not just the one already tested. (2) `memory` genuinely does **not** apply live without hotplug — resizing with `hotplug` unset produced `{"key": "memory", "value": "2048", "pending": "512"}`, the *old* value still what the running VM actually had. Exactly the caveat as documented, now confirmed. (3) **A real gotcha the original caveat didn't anticipate:** enabling `hotplug: memory` on an *already-running* VM doesn't retroactively grant it live-resize capability — the `hotplug` write itself showed as `pending`, same as `memory`, because QEMU's hotplug controller is a boot-time device that can't be added to a process already running. Confirmed by properly restarting the VM with `hotplug: memory` (and `numa: 1`, which Proxmox's memory hotplug also requires — restarting with NUMA on surfaced a second real gotcha, a `minimum memory must be 1024MB` start failure, since NUMA imposes its own floor) set *before* boot: a subsequent resize then showed a bare `value`, genuinely live. The CLI's one-line confirmation-prompt caveat stays terse on purpose — this level of nuance belongs in docs, not a `y/N` prompt.

**`resize_container` doesn't use docker-py's `container.update()`, and this was only discovered by testing against a real container, not by reading docker-py's docs.** `docker run --cpus=0.5` (the standard, common path — and how every earlier real-infra test container in this project was created) sets `HostConfig.NanoCpus`, not `CpuPeriod`/`CpuQuota`. A real `container.update(cpu_period=..., cpu_quota=...)` call against that same container fails with a genuine `409 Conflict`: `"CPU Period cannot be updated as NanoCPUs has already been set"` — Docker won't let a container mix the two CPU-limiting mechanisms. Worse, docker-py's `update_container()` (confirmed by reading its actual source, not just the docstring, in the installed `docker` 7.2.0) has **no `NanoCPUs` parameter at all** — it's simply not exposed by the convenience wrapper, even though the raw Docker Engine API accepts it (confirmed: the real `docker update --cpus` CLI command works against the same container and does set `NanoCpus`). `resize_container()` therefore posts the raw API request directly — `client.api.post(f"{client.api.base_url}/containers/{container.id}/update", data=json.dumps({"NanoCPUs": ..., "Memory": ...}))` — reusing docker-py's own `requests.Session` subclass and its already-registered Docker-socket transport adapter (both `.post()` and `.base_url` are genuinely public, stable attributes) rather than adding a new HTTP dependency or shelling out to the `docker` CLI binary, which nothing else in this codebase does. `docker.utils.parse_bytes()` (the same public helper `container.update()` uses internally) parses a human memory string (`"512m"`, `"1g"`) into raw bytes for the request body. Verified end to end against a real container: current-state display, a combined cpus+memory resize actually taking effect (confirmed via `docker inspect` before/after), and an intentionally-too-low memory value failing cleanly with a caught `400 Bad Request` rather than a crash.

**`atlas/actions/` is the real action registry**, added once a third action type existed to actually force the generalization (two entries were still just two ad-hoc dicts duplicated across files). `atlas/actions/targets.py` holds `known_container_names(environment)`/`known_guest_ids(environment)` (moved here from `atlas/intelligence/analyzer.py`, unchanged — pure functions over an already-collected environment dict, no Atlas-internal imports). `atlas/actions/registry.py` defines `ActionDefinition` (`type`, `command_template`, `known_targets`) and the `ACTIONS: dict[str, ActionDefinition]` singleton with all four entries. Still deliberately just a dataclass + dict, not a class hierarchy or plugin loader — four entries doesn't justify more machinery either, but it *is* now one place instead of three.

**`command_template` is a small callable (`Callable[[SuggestedAction], str]`), not a plain format string** — forced by `resize_container`, the first action needing more than one substitution. The three older entries are one-line lambdas (`lambda a: f"atlas restart {a.target}"`); `resize_container`'s conditionally includes `--cpus`/`--memory` only for whichever dimension was actually proposed, so a partial resize (just memory, just CPU) stays expressible rather than every suggestion being forced to restate both. Both CLI print sites (`atlas analyze`, `atlas chat`) call `definition.command_template(action)` directly now, passing the whole `SuggestedAction` rather than `.format(target=...)` — no per-action-type branching was added to the CLI to make this work, the callable already carries whatever each action needs. (`ActionDefinition` uses a `TYPE_CHECKING`-guarded string type hint for `SuggestedAction` to avoid a circular import — `atlas.intelligence.providers.base` already imports `ACTIONS` from this module.)

**`atlas analyze`/`atlas chat` suggest actions**, all driven by that one registry now. Each `Recommendation`/`ChatReply` can carry an optional `action: SuggestedAction | None` (`type`, `target`, `cpus`, `memory`) — schema-validated via a single shared `ACTION_SCHEMA` (an `anyOf` of the action object or `null`) that both `ANALYSIS_SCHEMA` and `CHAT_SCHEMA` reference by identity rather than each duplicating their own copy of the action-object shape. `cpus`/`memory` are required-but-nullable on *every* action type (same "structured output requires every key in `required` even when the value is nullable" reasoning `action` itself already needed) — meaningful only for `resize_container`/`resize_guest`, always `null` on the other four; `SuggestedAction(**action_data)` picks them up for free since they're just two more dataclass fields with `None` defaults, no special-casing needed in `recommendation_from_dict()`/`chat_reply_from_dict()`. `ACTION_SCHEMA`'s `type` enum is `list(ACTIONS.keys())` — derived, not hand-written, so the schema can't drift out of sync with what the analyzer/CLI actually know how to handle. `ACTION_INSTRUCTIONS` (shared by `SYSTEM_PROMPT` and `CHAT_SYSTEM_PROMPT`) still hand-writes the natural-language grounding rule per action (auto-generating that prose isn't worth it for four entries) and needs its own sentence added per new action — `resize_container`'s spells out that `cpus`/`memory` take a new-limit string or `null` to leave that dimension unchanged, and that at least one must be non-null. Before returning, `AtlasAnalyzer.analyze()`/`AtlasAgent.converse()` look up `ACTIONS.get(action.type)` and clear the action if the type isn't in the registry or the target isn't in `definition.known_targets(environment)` — a resize suggestion with both `cpus`/`memory` null isn't specially caught here (it would just render as `atlas resize <target>` with no flags); `atlas resize`'s own CLI validation is the actual safety net for that case, the same boundary that already has to validate its own inputs regardless of where a suggestion came from. `atlas analyze`/`atlas chat` only *print* a matching suggestion via `definition.command_template(action)`; neither executes it — that stays a separate, explicit invocation with its own approval gate. **Adding a fifth action type now means one `ACTIONS` entry, one manager function, one CLI command, and one `ACTION_INSTRUCTIONS` sentence — not three separately-maintained dicts.**

**Persistence.** SQLite via SQLAlchemy, engine at `atlas/database/engine.py` pointing at `inventory/atlas.db`. `atlas/database/models.py` holds the ORM models (`EventRecord`, `EnvironmentRecord`, `AnalysisRecord`); `atlas.database.initialize_database(engine=None)` runs `Base.metadata.create_all` (idempotent — only creates tables that don't exist yet) and also ensures `inventory/` exists whenever the engine being initialized is the default one (compared by identity against `atlas.database.default_engine`, **not** `engine is None`). Every method on `KnowledgeStore` and `KnowledgeQueries` calls `initialize_database(engine)` — using its own module's locally-bound `engine` name — as its first line, so tables self-heal lazily at the moment of actual use. **This has to be call-site, not `__init__`-site or `AtlasRuntime.__init__`-site**: `DatabaseListener` (and therefore a `KnowledgeStore`) is constructed as part of the `AtlasApplication()` singleton at *module import time* (see above), using whatever the process's cwd happens to be then — for `pytest` run from the repo root, that's the real repo. Putting table-creation in any constructor in that chain silently mutates the committed `inventory/atlas.db` on every test run; this was caught and reverted while fixing the bug below. New tables just need a model added to `models.py` — no new wiring, since every call site already re-runs `create_all`. Reads and writes are split: `atlas/knowledge/store.py` (`KnowledgeStore`) writes, `atlas/knowledge/queries.py` (`KnowledgeQueries`) reads (`latest_environment()`, `latest_analysis()`, `recent_events()`). `inventory/atlas.db` is gitignored (not committed) — it grows a new row on every command run and now self-heals its own schema via `initialize_database()`, so there's nothing to seed; it was committed to git early in the project's life, which caused the bug described next, and was un-tracked once that was fixed.

**The previously-committed `inventory/atlas.db` predated `AnalysisRecord` and was missing the `analysis` table**, and nothing ever called `initialize_database()` automatically — so `atlas analyze` would crash with `sqlite3.OperationalError: no such table: analysis` on first real use, for anyone, including against this exact repo. Fixed by the lazy per-call-site `initialize_database()` above; verified by copying the (then still committed) db into an isolated tempdir, confirming the missing table gets added with existing rows untouched.

**A related directory-creation bug in that same fix went undetected until the Proxmox restart action needed it**: the original `initialize_database()` only created the missing `inventory/` directory when called with `engine is None`, but no real call site ever calls it that way — `KnowledgeStore`/`KnowledgeQueries` always pass their own bound `engine` explicitly, which *is* `default_engine` in real usage but fails an `is None` check. This never surfaced because every prior manual verification happened to run `atlas discover` first, and `save_inventory()` (a completely separate code path, for the YAML inventory file, not the database) incidentally creates `inventory/` as a side effect — masking the gap for any command run after it. It surfaced when testing `atlas proxmox restart` from a truly empty directory with no prior `atlas discover` call. Fixed by comparing identity against `default_engine` instead of `None`. Caught **again** while writing the regression test: a naive `isolated_cwd`-only test reusing the real `atlas.database.engine.engine` singleton silently read/wrote the developer's actual local `inventory/atlas.db`, because SQLAlchemy's sqlite dialect resolves a relative database path to an absolute one once, at `create_engine()` time (module import, whatever cwd that happens to be), not per-connection like raw `sqlite3.connect()` does — so reusing that singleton across an in-process `chdir()` (exactly what `isolated_cwd` does) doesn't behave like a real second `atlas` invocation. Not a product bug (a real CLI process never changes its own cwd mid-run), but a real test-safety hazard: the regression test (`tests/test_knowledge.py`) uses a fully separate, absolute-path engine instead, monkeypatching `atlas.database.DATABASE_PATH`/`default_engine` directly rather than touching the shared singleton.

**`save_environment()` is insert-only.** Every call adds a new `EnvironmentRecord` row (its own `created_at`); nothing ever updates one in place. So a full history of past snapshots already exists even though only `latest_environment()` (the newest row) is normally queried — **check this before concluding a diffing/history feature needs new schema.** Proxmox change detection (`atlas/proxmox/changes.py`) is the only consumer so far: `atlas proxmox scan` calls `latest_environment()` *before* saving its own results, so "latest" at that point is actually the previous scan — free baseline, no new table or query method. The roadmap previously claimed this exact feature needed "time-series storage" before anyone actually checked; it didn't.

**Proxmox change detection.** `diff_virtualization(previous, current)` (`atlas/proxmox/changes.py`) is a pure function comparing two `{"nodes": [...], "guests": [...]}` dicts — nodes matched by `name`, guests matched by `vmid` (the stable Proxmox identifier; don't match guests by name, a rename would show as remove+add). Returns `[]` when `previous` is falsy (no baseline yet) rather than treating a first sighting as synthetic "added" noise. `format_change()` renders one change dict to a display string; `atlas/cli/main.py`'s `scan()` only publishes `atlas.proxmox.changes_detected` when the list is non-empty, so a no-op scan doesn't add event-log noise.

**Both `atlas proxmox scan` and `atlas proxmox restart` have now been run against a real Proxmox VE host** (not just mocks) — scan correctly connected via API token and found the real node, then correctly detected a newly-created LXC guest as an addition on the next scan; restart then successfully restarted that real guest. Anthropic is partially verified (auth + error-handling path confirmed, full response deferred — see roadmap); Ollama and Prometheus status are also tracked there. Don't claim Proxmox discovery/restart are unverified going forward; they aren't anymore. Two real Proxmox-side gotchas surfaced getting `restart` working, both documented in `docs/deployment/index.md` rather than repeated here: `verify_ssl: true` fails against Proxmox's default self-signed cert, and the API token's **Privilege Separation** setting (on by default) means permissions granted to the *user* don't apply to the *token* unless separation is off or the grant targets the token identity directly.

**Monitoring.** `atlas monitor` (`atlas/cli/main.py`, backed by `atlas/monitoring/`) queries an existing Prometheus server rather than Atlas exposing its own `/metrics` endpoint — same "Atlas reaches out on command" shape as `atlas discover`/`atlas proxmox scan`. `client.py`'s `query_prometheus(base_url, promql)` hits `/api/v1/query`; it **raises** `PrometheusUnavailableError` on connection failure or a non-success API response, but **returns `None`** (not an error) when a query is simply empty — `collector.py`'s `collect_metrics()` relies on that distinction to set `available` (Prometheus reachable at all) independently of each metric being `None` (that specific query had no data, e.g. an exporter isn't running). The three default queries (`CPU_QUERY`/`MEMORY_QUERY`/`DISK_QUERY` in `collector.py`) assume standard `node_exporter` metric names — a second metric source means adding queries there, not inventing a new module, which is exactly what happened for cAdvisor container metrics (see below). Results land in `AtlasEnvironmentContext.monitoring` (added alongside `containers`/`virtualization` — remember `.update()` only sets attributes that already exist on the context, so a new top-level category needs the field added to `__init__`/`summary()` first, same as this one was). **This integration has now been verified against a real Prometheus** (Docker, `prom/prometheus` + `prom/node-exporter`, host networking) — all three default queries resolved against real metric names and returned real values, and the full `atlas monitor` scan→save→print path worked end to end. Don't claim it's mock-only going forward; that was true earlier in the project but isn't anymore — see the roadmap's "Verification against real infrastructure" entry.

**Threshold flagging.** `collector.py`'s `evaluate_thresholds(metrics, thresholds)` is a pure function (`{metric_name: bool}`, `>=` comparison) — a metric that's `None` or has no configured threshold is left out of the result entirely, not counted as "not exceeded"; those are genuinely different states and the CLI treats them differently (unavailable vs. green vs. yellow). Thresholds live on `MonitoringConfig` as `cpu_threshold`/`memory_threshold`/`disk_threshold`, `90.0` each by default — the same number `atlas/health/checks.py` already uses for the local host's own memory/storage checks, reused deliberately rather than picking a new number. `monitor()` in `atlas/cli/main.py` prints `✓`/`!` per metric (mirroring `atlas doctor`'s convention) and publishes `atlas.monitoring.threshold_exceeded` only when `any(exceeded.values())` — same "don't log a no-op" rule as `atlas.proxmox.changes_detected`, not published on every scan regardless of outcome.

**Container-level metrics (cAdvisor).** cAdvisor is treated as a second exporter scraped by the same Prometheus `atlas monitor` already queries, not a new integration — no new config section, just two more PromQL queries. `client.py`'s `query_prometheus()` only ever returned a single scalar (`result[0]`), which doesn't fit a query that returns one row per container; the shared request/parse logic moved into a private `_query()`, and a new `query_prometheus_vector(base_url, promql, label)` returns `{label_value: value}` for every row in the result, keyed by a caller-given Prometheus label (`"name"` for cAdvisor's container label). `collector.py`'s `collect_container_metrics()` runs two cAdvisor queries through it — CPU as percent of one core (`rate(container_cpu_usage_seconds_total[5m])*100`, the standard cAdvisor/Grafana convention) and memory as percent of host total memory (`container_memory_usage_bytes / scalar(node_memory_MemTotal_bytes) * 100`, deliberately the same unit as the host's own `memory_percent` so `evaluate_thresholds()` and the existing `cpu_threshold`/`memory_threshold` config work unchanged, called once per container). A container missing from one of the two queries still appears with `None` for that metric — same "no data yet, not an error" rule the host collector already follows. Results merge into the same `AtlasEnvironmentContext.monitoring` dict under a `containers` key, no new context field.

**Monitoring change detection.** `atlas/monitoring/changes.py`'s `diff_monitoring(previous, current, thresholds)` mirrors `atlas/proxmox/changes.py`'s `diff_virtualization()` shape (same `previous`-falsy → `[]` no-baseline rule) but diffs *threshold-exceeded state* rather than raw state: a metric — host or per-container — moving from under-threshold to over-threshold since the last scan is a `*_metric_crossed` change, the reverse a `*_metric_recovered`. Both snapshots are evaluated against the *current* thresholds, not whatever was configured when the previous snapshot was saved — threshold config isn't versioned per snapshot, so re-checking old data under today's config is the only comparison that means anything. `format_change()` is imported into `atlas/cli/main.py` aliased as `format_monitoring_change`, since the unaliased name is already bound to the Proxmox version. `monitor()` fetches `KnowledgeQueries().latest_environment()` up front (same placement as `atlas proxmox scan`) and publishes `atlas.monitoring.changes_detected` only when non-empty — a genuinely different event from the existing `atlas.monitoring.threshold_exceeded` (fires on "something is bad right now," every scan) versus this one firing on "something changed since last time."

**Container resource-allocation visibility.** `atlas monitor` now also answers "is this container starved relative to what it was actually *allocated*," not just "is it busy" — `cpu_percent`/`memory_percent` are already percent-of-*host*; `collect_container_metrics()` gained two more optional per-container keys, `cpu_percent_of_limit`/`memory_percent_of_limit`, percent of the container's *own* configured limit. **Deliberately no Docker-side collection** — the original framing assumed this needed `docker.py`'s `container.attrs["HostConfig"]` cross-referenced against cAdvisor usage by name, but cAdvisor already exposes the configured limits themselves as their own metrics (`container_spec_cpu_quota`/`container_spec_cpu_period`, `container_spec_memory_limit_bytes`), so the whole thing is two more PromQL queries in `collector.py`, computing "percent of own limit" entirely server-side — no cross-collector join, `atlas/docker/manager.py` untouched. Confirmed against real cAdvisor: an unconstrained container's `container_spec_cpu_quota` series doesn't exist at all (not zero — the query naturally returns no row, no special-casing needed), while `container_spec_memory_limit_bytes` **does** return a row at `0` for unconstrained containers, needing an explicit `> 0` filter to treat as "no limit configured" the same way. **A real PromQL bug, only caught by running against real cAdvisor, not by unit tests against mocks:** `CONTAINER_CPU_LIMIT_PERCENT_QUERY` divides an aggregated `sum(...) by (name)` series (which strips every label except `name`) against the un-aggregated `container_spec_cpu_*` series (which still carry their full original label set) — Prometheus's default one-to-one vector matching requires identical label sets and silently returns *no rows* rather than an error when they don't match, so every container's `cpu_percent_of_limit` came back `None` even for the one with a real configured limit. Fixed with explicit `on(name)` matching on both operators. The memory query didn't need this — neither side of that division is aggregated, so both retain cAdvisor's full original label set and match by default. Verified end-to-end against a real `--cpus=0.5 --memory=256m` test container: `cpu_percent_of_limit` tracked `cpu_percent / 0.5` exactly across several live scans, and `cpu_allocation_threshold`/`memory_allocation_threshold` (two new `MonitoringConfig` fields, same 90.0-default convention as every other threshold) correctly flagged it with `!` once lowered below the real live percentage.

**A second real correctness gap, found while tracing the display path, not by running anything:** `atlas monitor`'s per-container print loop calls `evaluate_thresholds(values, thresholds)`, and `evaluate_thresholds()` already correctly excludes a metric with no matching key in `thresholds` from its result. Without `cpu_allocation_threshold`/`memory_allocation_threshold` existing as literal keys the container-level call passes through, `cpu_percent_of_limit`/`memory_percent_of_limit` would print a real value but **silently never show the yellow `!`**, even at 100% of allocation — not a crash, just a quiet false "healthy," since the `thresholds[name]` indexing that renders the threshold value only executes inside the `if exceeded:` branch, which a missing key means is never true. Fixed by building a second, container-only thresholds dict (`{**host_thresholds, "cpu_percent_of_limit": ..., "memory_percent_of_limit": ...}`) rather than adding the two new keys to the host-level dict, which stays exactly 3 keys. This same merged dict is what's now passed to `diff_monitoring()` too — `evaluate_thresholds()`'s existing "unknown key = not evaluated" behavior means the host-level evaluation inside `diff_monitoring()` is completely unaffected by the two extra keys being present.

**Zero changes to `diff_monitoring()`, `evaluate_thresholds()`, or the `atlas.monitoring.changes_detected` event path** — both are already generic over whatever keys appear in a container's metrics dict, so a container crossing 90% of its own limit between two scans produces a real `container_metric_crossed` change and publishes the existing event for free. Confirmed directly: not by re-deriving the logic, but by noting it's the exact same unmodified code path already real-verified for host/container `cpu_percent`/`memory_percent` in the original cAdvisor work. This is the third time this project has found "the thing we assumed needed new infrastructure didn't" — after Proxmox's insert-only history and the event-listener registration gap.

**Both cAdvisor container metrics and monitoring change detection have now been verified against real infrastructure** — a real cAdvisor container (Docker, host networking, `--privileged`) added as a second scrape job on the same test Prometheus used for the earlier monitoring verification. `atlas monitor` correctly returned real per-container CPU/memory for all three actual containers running on the host, and lowering `cpu_threshold` below live CPU usage between two real scans produced a genuine `container_metric_crossed` change and `atlas.monitoring.changes_detected` event — while correctly *not* flagging the host CPU metric as changed, since re-evaluating the previous snapshot under the new threshold showed it was already over, exactly the "evaluate both snapshots against current thresholds" behavior described above working as intended on real data. Don't claim this is mock-only going forward.

**Resource-usage trending (`atlas trends`).** `save_environment()` (`atlas/knowledge/store.py`) is insert-only, so a full history of past snapshots already existed in the `environment` table — this is the fourth time this project has found "the thing we assumed needed new infrastructure didn't," after Proxmox's insert-only history, the event-listener registration gap, and the cAdvisor allocation-visibility work above. `KnowledgeQueries.environment_history(limit=20)` is a new method (same shape as `recent_events()`, right above it) returning parsed `{"created_at", "data"}` rows, most-recent-first (ordered by `created_at.desc(), id.desc()` — the `id` tiebreak matters, since two real snapshots can land in the same microsecond). `atlas/monitoring/trends.py` (new, pure functions, same style as `atlas/monitoring/changes.py`) turns that into chronological `(timestamp, value)` points per metric via `host_metric_trend()`/`container_metric_trend()`, plus `known_container_names()` to enumerate which containers appear anywhere in the window. `atlas trends` prints one summary line per metric (latest/min/max/avg over N samples), no graphs — same plain-text convention every other command uses.

**A real caveat that shaped the whole design, found by reading the actual save call sites, not assumed:** `atlas discover`, `atlas proxmox scan`, and `atlas monitor` all call `save_environment()`, but each CLI invocation is a separate process with its own fresh `AtlasEnvironmentContext()` — so **every saved row only carries the categories that specific command populated**, never a complete snapshot. A row from `atlas monitor` has real `monitoring` data but empty `hardware`/`virtualization`; a row from `atlas discover` is the reverse. `host_metric_trend()`/`container_metric_trend()` therefore explicitly skip any row missing `monitoring` entirely (not just a missing metric within it) rather than assuming every row is a full snapshot. This is also why the scope stayed to host + per-container metrics, both saved together by `atlas monitor` in one row — merging in Proxmox guest usage would mean stitching together two independently-scheduled snapshot series and normalizing units (Proxmox's guest `cpu` is a 0–1 fraction, not a percent), deliberately deferred as its own follow-up rather than folded in here. Verified against real accumulated history: several real `atlas monitor` runs against the existing test Prometheus + cAdvisor setup, then `atlas trends` correctly reported genuine host and per-container trends for every real container, including `cpu_percent_of_limit`/`memory_percent_of_limit` trending correctly for the one container with a real configured limit and showing nothing for the unconstrained ones.

**`--json` output + cron-friendly exit codes (`atlas doctor`/`atlas monitor`/`atlas trends`).** All three commands gained a `--json` flag (Python parameter `json_output`, not `json`, so it doesn't shadow the stdlib module) printing a single machine-readable payload via plain `print(json.dumps(payload, indent=2))` — deliberately **not** `console.print()`, since Rich's terminal handling isn't the concern for output piped into `jq`/a cron log with no TTY attached. **Exit codes are meaningful all the time, not gated behind `--json`** — `atlas doctor`/`atlas monitor` now `raise typer.Exit(code=1)` whenever something's actually wrong (an unhealthy check, an exceeded threshold, an unreachable Prometheus), regardless of output format, so a plain cron job can just check `$?` with no JSON parsing at all. This is a real, deliberate behavior change from the previous always-exit-0 behavior — confirmed nothing in this project depended on the old behavior before making the change. `atlas doctor`'s `healthy` is `all(check["status"] for check in results)`, computed once and used for both the JSON payload's `"healthy"` key and the exit check, so they can never disagree. `atlas monitor` distinguishes three states in its JSON shape — disabled (`{"enabled": false}`, exit 0, since disabled is an intentional state, same rule `atlas doctor` already applies to every optional integration), unreachable (`{"enabled": true, "available": false}`, exit 1, since you configured and expected Prometheus and it's not there), and reachable (full payload with `metrics`/`thresholds`/`exceeded`/`containers`/`changes`/`healthy`, exit 1 iff any host or per-container metric exceeded its threshold) — every field reuses a variable the function already computes for the human-readable path, no new calculation. `atlas trends` gets **no** exit-code logic — it has no health/threshold concept to signal (a trend report with zero samples is empty, not wrong), so only `--json` output was added there; needed one real restructuring, pulling the inline latest/min/max/avg/samples computation each print statement did directly into a shared `_trend_summary(points)` helper, so the human and JSON paths compute identical numbers from the same call instead of two parallel implementations. Verified against real infrastructure: `atlas doctor --json`/`atlas monitor --json`/`atlas trends --json` all produced genuinely valid JSON (piped through `jq` against the real Docker/Prometheus/cAdvisor test setup, not just "didn't crash") with real live values matching the human-formatted output; `atlas monitor`'s exit code was confirmed to actually flip from `0` to `1` and back by temporarily lowering `cpu_threshold` below the real live CPU percentage and then restoring it.

**Discovery: built-in + plugins, unified in `atlas discover`.** `atlas.discovery.run_discovery()` (`atlas/discovery/__init__.py`) is the built-in, synchronous path — it directly calls `collect_system/hardware/storage/network` and returns a merged dict. Separately, `atlas/plugins/` implements a plugin architecture (`AtlasPlugin` ABC with `initialize(runtime)` / `discover()`, `PluginManager.load_plugins()` auto-discovers via `atlas/plugins/loader.py`, `discover_all()` runs every registered plugin, currently just a Docker plugin). The `atlas discover` CLI command (`atlas/cli/main.py`) runs both in one pass: built-in results go through `AtlasEnvironmentContext.ingest_discovery()`, plugin results go through `.update("containers", plugin_data)`, and both are saved to the knowledge store in a single `save_environment()` call before two separate events publish (`atlas.discovery.completed`, `atlas.plugins.discovery.completed`). There used to be a separate `atlas discover-plugins` command; it was removed once its job was folded into `atlas discover` — don't reintroduce it as a distinct command without a reason, the whole point was one discovery entry point. `atlas plugins` (list registered plugins, no discovery) is unrelated and still exists.

**Config.** `atlas/config/loader.py`'s `load_config()` reads `atlas.yaml` from the current working directory (returns `AtlasConfig()` defaults if the file doesn't exist) and validates it against the pydantic models in `atlas/config/models.py`. Config sections are added by adding a new pydantic `BaseModel` subclass and a field on `AtlasConfig`, following the existing `ProxmoxConfig`/`IntelligenceConfig` pattern. `atlas/config/config.yaml`, a stray unused template fragment nothing ever read, was deleted once `atlas init` (below) became the real answer to "how do I get a config file."

**`atlas init`** (`atlas/cli/main.py`) interactively builds an `AtlasConfig` and writes it via `atlas/config/writer.py`'s `write_config(config, path=CONFIG_FILE)` — plain `yaml.safe_dump(config.model_dump())`, no prompting, reusing `loader.py`'s `CONFIG_FILE` constant rather than redefining it. Only prompts for fields that actually vary per deployment (name, Proxmox, AI provider, Prometheus) — `discovery`/`inventory` stay at their pydantic defaults, never asked about. All interaction (`typer.prompt`/`typer.confirm`) lives in the CLI command, same split as `atlas restart`/`atlas proxmox restart`: manager/config modules stay pure, the CLI layer owns stdin/stdout. `write_setup_log(lines, directory=Path("logs"))` writes a plain-text `atlas-init-<timestamp>.log` (the CLI command builds up `lines` as a list of strings while prompting) — `logs/` was already gitignored before this, no `.gitignore` change needed. **The log never contains secret values** (`token_value`/`password`), only that one was set and which auth method was chosen (`auth=token`/`auth=password`) — deliberately a different exposure bar than `atlas.yaml` itself, which already stores the Proxmox secret in plaintext (existing, pre-`init` precedent) since a log is the kind of file that tends to get pasted into a troubleshooting thread. `ANTHROPIC_API_KEY` is never prompted for or written anywhere, consistent with how it already worked — `init` just prints a reminder to set it as an environment variable. Overwriting an existing `atlas.yaml` is gated behind `typer.confirm()` like every other mutating command in this codebase; declining aborts before anything is written or logged.

**Found while building `atlas init`**: the real local `atlas.yaml` had `name: sentinel` nested under a stray top-level `atlas:` key that `AtlasConfig` doesn't define — pydantic's default `BaseModel` behavior silently ignores unrecognized top-level keys rather than erroring, so `name` had been quietly falling back to the default `"atlas-node"` the whole time `atlas.yaml` existed. Not the kind of thing to hand-patch; a fresh `atlas init` run naturally produces a correctly-shaped file going forward.

**`atlas init`'s `hide_input=True` on the token/password prompts was removed** after a real user report: some terminal environments don't render the erase sequence a canonical-mode TTY sends back for backspace correctly, showing duplicated/garbled characters while typing. Reproduced with `pexpect` (a real pty; piped `stdin` doesn't exercise this at all, since there's no line editing to get wrong) and confirmed the *parsed value* was always correct regardless — `typer.prompt(..., hide_input=True)` and plain `typer.prompt()` both process backspace correctly at the OS/readline level; what was broken was purely the terminal's own rendering of the echo, outside anything Atlas's Python code controls. Since the destination is a local file that already stores these values in plaintext (see above), hiding keystrokes during entry wasn't earning much anyway, and removing it happens to sidestep the rendering bug's most confusing case (a secret) even though the same rendering issue can technically still affect any prompt. The actual fix for "did what I typed actually come through right" is the **review screen** added right before `write_config()`: it re-prints every field from the already-built `AtlasConfig` (never from the loose per-branch local variables, which don't all exist when a section was skipped) and gates on one final `typer.confirm()`. Secrets show as `"N characters entered"`, never the value, in the review — this is deliberately still visible in the terminal session's own output when using `runner.invoke()` in tests (that's the whole point of removing `hide_input`), just never in the setup log.

**Health checks.** `atlas/health/checks.py`'s `run_checks()` (backing `atlas doctor`) returns a flat list of `{"name", "status", "details"}` dicts — five environment checks (Python/memory/storage/Docker/inventory) plus three integration-readiness checks (`check_proxmox`, `check_intelligence`, `check_monitoring`), each taking the loaded `AtlasConfig` and reporting whether that integration is *configured* (host/credentials/API key/URL present), not whether it's actually *reachable* — no network calls, so `doctor` stays fast and can't hang. A disabled integration (`enabled: false`) reports `status: True` — disabled is a valid, intentional state, not something to flag red; only "enabled but missing what it needs" is unhealthy. Real reachability is still unverified until the integration is actually run — see the roadmap's "Verification against real infrastructure" entry.

**AI providers.** `atlas/intelligence/providers/` defines an `AIProvider` ABC (`base.py`) returning a schema-shaped `AnalysisResult`/`Recommendation`; `AnthropicProvider` and `OllamaProvider` both use structured/schema-constrained output so responses never need free-text parsing. `get_provider(config.intelligence)` is the factory (provider implementations are imported lazily inside it so the `anthropic` import isn't required just to build the config or use the Ollama path). `AtlasAnalyzer` (`atlas/intelligence/analyzer.py`) is a thin wrapper that just delegates to whichever provider it's given — put orchestration logic there, not in the CLI command.

**Agent-based capabilities: tool-use + `atlas chat`.** `atlas/intelligence/tools.py`'s `build_tools(config)` returns `{name: ToolDefinition}` — a small, deliberately **read-only** set (`get_containers`, `get_services`, `get_recent_events`, `get_last_analysis`, `get_container_logs`, plus `get_proxmox_status`/`get_monitoring` when those integrations are enabled), each just wrapping a function that already exists elsewhere (`collect_containers()`, `discover_resources()`, `collect_metrics()`, etc.) — no new data-collection code. `execute_tool()` is the shared dispatcher; an unknown tool name or a handler exception becomes `{"error": ...}` rather than raising, so a hallucinated tool call can't crash a session. No mutating tool exists here on purpose — restart/stop stay behind their own approval-gated commands, never reachable mid-analysis. `AIProvider.analyze()` gained an optional `tools` param (default `None`, so every existing no-tools call site is unchanged) and a new `converse(messages, tools) -> ChatReply` method backing the new `atlas chat` command; `converse()` is **not** `@abstractmethod` (raises `NotImplementedError` by default) so a provider or test double implementing only `analyze()` stays a valid `AIProvider`. `atlas analyze` passes `build_tools(settings)` by default — no config flag, since unlike Prometheus/Proxmox this has no external dependency to gate against, only data Atlas can already collect locally.

**`get_container_logs` was the first tool needing an argument, which exposed a real gap: `ToolDefinition.handler` was `Callable[[], dict]` and `execute_tool(tools, name, arguments)` never actually passed `arguments` to the handler** — every existing tool got away with this since they all used `EMPTY_SCHEMA`. Both providers' tool-use loops were already correctly extracting real per-call arguments from the model (`block.input` in `anthropic_provider.py`, `function.get("arguments")` in `ollama_provider.py`) and passing them into `execute_tool()` — the plumbing existed one layer up, it just silently dead-ended at the dispatcher. Fixed by changing every handler's signature to `Callable[[dict], dict]` (the five existing zero-arg handlers just take and ignore `arguments` now, uniformly, rather than special-casing the one that needs it — same reasoning `command_template` becoming a callable for every action, not just `resize_container`, already established) and having `execute_tool()` call `definition.handler(arguments)`. `get_container_logs(container, tail)` wraps a new `get_container_logs()` in `atlas/docker/manager.py` (same pure-result-dict, never-raises shape as `get_container_info`/`stop_container`, using `container.logs(tail=N, timestamps=False)`, decoded with `errors="replace"` since container output isn't guaranteed clean UTF-8). `tail` is model-controllable but server-side capped at 500 regardless of what's requested, so a runaway request can't dump excessive log volume into the conversation. No grounding logic needed here unlike a suggested action — a hallucinated or stale container name just comes back as a normal `{"found": False, "error": "No container named '<x>' found"}` tool result via Docker's own `NotFound` handling, the same path `get_container_info`/`restart_container`/`stop_container` already use.

**The two providers' tool loops are deliberately not the same shape — this was forced by real testing, not a style choice.** Anthropic sends `tools` and the schema-constrained `output_config.format` in the *same* request every turn (Anthropic's documented pattern); a `tool_use` stop reason means execute and loop, anything else means parse the final schema-shaped answer. **Ollama never sends `tools` and `format` together** — verified against a real local `llama3.1`: with both present, the model silently never emits `tool_calls` at all and just answers directly and ungrounded, no error, just quietly wrong (worse than a normal miss, since nothing signals it happened). The initial combined-request implementation passed every unit test against a mocked client and still had this bug — it only surfaced by actually running `atlas chat` against the real model. Fixed by running Ollama's tool-gathering phase with `tools` but no `format` until the model stops asking for tools, then one dedicated finalize request with `format` and no `tools`. When no tools are offered at all, both providers collapse back to exactly one request — the original pre-tool-use behavior, unchanged.

**`atlas chat`** (`atlas/cli/main.py`) is the new interactive command: `messages` persists for the session's lifetime only, driving the provider — see below for how the transcript itself is now separately persisted. `AtlasAgent` (`atlas/intelligence/agent.py`) is chat's counterpart to `AtlasAnalyzer`, applying the identical `ACTIONS.get(action.type)` + `known_targets(environment)` grounding check before ever surfacing a suggested action. The one real difference: chat has no guaranteed prior `atlas discover` to ground against, so `AtlasAgent._live_environment()` builds a minimal grounding dict by calling live state through the *same* tool the model itself can call (`execute_tool(self.tools, "get_proxmox_status", {})`) rather than a second copy of the Proxmox connection logic. Stays strictly on-demand like every other command — no daemon, no scheduled mode.

**Verified against a real local Ollama (`llama3.1`)**: `atlas chat` correctly called `get_containers` mid-conversation and reported the real, live set of Docker containers running on the host, not a stale snapshot or a hallucination — this is the run that caught the tools+format bug above.

**Multi-step action plans.** A `Recommendation`/`ChatReply`'s existing single `action` field only ever expressed one independent suggestion; `AnalysisResult`/`ChatReply` now also carry an optional `plan: SuggestedPlan | None` — `SuggestedPlan(summary, steps)`, each `PlanStep(action, rationale)` — for a genuine ordered sequence where later steps depend on earlier ones (e.g. stop the container holding a lock, then restart the one that was failing because of it). **This is still suggest-only, the same as every single `action` before it** — `atlas analyze`/`atlas chat` print the plan as a numbered list with each step's rationale and its `definition.command_template(step.action)`; nothing executes it. There's no `atlas plan run`, no plan persistence (`KnowledgeStore.save_analysis()` is untouched and still only writes `summary`/`recommendations`), and no changes to how any action actually runs — each step is still run by literally typing the printed command yourself, one at a time, through its own existing approval gate. `PLAN_SCHEMA` (`atlas/intelligence/providers/base.py`) reuses `ACTION_OBJECT_SCHEMA` (pulled out of `ACTION_SCHEMA` for this) for each step's action — unlike the standalone `action` field, a plan step's action isn't nullable, since a step without one doesn't mean anything. `PLAN_INSTRUCTIONS` (appended to both `SYSTEM_PROMPT` and `CHAT_SYSTEM_PROMPT`) tells the model to use a plan only for a genuine multi-step dependency, not as a container for several unrelated independent issues — those should stay separate `Recommendation`s, each with its own `action`. Grounding treats a plan as one coherent unit, not a bag of independent steps: `AtlasAnalyzer.analyze()`/`AtlasAgent.converse()` already null out any `Recommendation.action`/`ChatReply.action` whose target isn't in `definition.known_targets(environment)` (via the shared `is_action_grounded()` helper, factored out of both call sites into `atlas/actions/registry.py` once this made it the third place doing the identical check); for a plan, one hallucinated step target drops the **entire plan**, not just that one step — running step 1 of a plan whose step 2 turns out to be fabricated could leave things worse off than either a complete plan or no plan at all.

**Found only by running a real plan through a real local Ollama, not by any unit test**: the model filled in *both* `plan` and the standalone `action` for the same suggestion — `action` came back as a copy of the plan's own first step, which would have printed a redundant "suggested action" line directly above the plan that repeats its own step 1. `PLAN_INSTRUCTIONS` was updated to tell the model not to do this, but — same reasoning as target grounding — a prompt instruction isn't enforcement, so `AtlasAgent.converse()` also nulls `reply.action` outright whenever `reply.plan` is present, after grounding. Re-ran the same live Ollama scenario (a genuine 3-step stop/restart/restart dependency chain across two real Docker containers) after the fix: the plan came back correctly grounded and ordered, and `action` came back `None`. A second live run — two containers with one simply exited, no real dependency between them — correctly produced two independent recommendations and left `plan` `None`, confirming the model isn't defaulting to a plan when a plan isn't warranted.

**Plan execution.** `atlas analyze`/`atlas chat` no longer just print a plan and stop — right after printing, both ask `"Run this plan now?"`, and if confirmed, run each step in order, each with its **own** `typer.confirm()` (not one blanket "run the whole plan" gate) via a new `execute_action(action) -> dict` dispatcher in `atlas/actions/registry.py`. `ActionDefinition` gained a fourth field, `executor: Callable[["SuggestedAction"], dict]`, alongside `command_template`/`known_targets` — `execute_action()` just does `ACTIONS[action.type].executor(action)`, the "generic runner that dispatches without hardcoded per-type branches" a much earlier deferred version of this idea called for. The four Docker executors are trivial one-line lambdas wrapping the same manager functions the standalone `atlas restart`/`stop`/`resize` commands already call. The three Proxmox executors share a new `_execute_guest_action(action, manager_fn, **extra_kwargs)` helper that connects and calls `get_guest_info()` first — exactly what `restart_guest_command`/`stop_guest_command`/`resize_guest_command` already do inline, just factored into one place instead of three; this is the piece the original deferral called "materially harder," and it turned out to just be the same connect-then-lookup preamble every Proxmox CLI command already has. `atlas/actions/registry.py` previously imported nothing beyond `atlas.actions.targets`; it now imports `atlas.docker`, `atlas.proxmox`, and `atlas.config` too (checked for circular imports first — none of the three import back from `atlas.actions` or `atlas.intelligence`, where `ACTIONS` is also imported).

**Scope was deliberately narrower than the original deferred idea.** That idea assumed plan persistence was needed for a separate `atlas plan run` command. It isn't: the plan object already exists in memory the instant it's printed, so `atlas analyze`/`atlas chat` just offer to run it right there — no new command, no persisted "last plan" slot, no way to come back and run an old one later. This is also more consistent than the persisted version would have been: there's no "run my last suggestion" mechanism for a single suggested `action` either, so a plan not getting one keeps both codepaths following the same rule. A declined or failed step always stops the rest of the plan (never skip-and-continue) — a plan exists specifically for steps with a real dependency on each other, so running step 3 after step 2 didn't happen could leave things worse off than doing nothing. Each executed step publishes the **exact same event type** the matching standalone command already publishes (`atlas.action.container_restarted`, `atlas.action.guest_stopped`, etc., via a small `PLAN_STEP_EVENT_TYPES` lookup in `atlas/cli/main.py`) so it shows up in `atlas history` indistinguishable in effect from a manually-typed command — only `source="PlanStep"` (instead of `"RestartAction"`/`"ProxmoxStopAction"`/etc.) differs, preserving provenance. Deliberately **no "current state" display before confirming a step**, unlike every standalone command — replicating that would need a per-action-type info lookup inside the CLI's plan loop, exactly the branching this feature exists to avoid; the step's already-known rationale and exact templated command are what's shown instead, a real (accepted) trade-off, not an oversight.

**Verified against a real local Ollama and the real Docker test containers, executing for real, not just printing:** the same genuine 3-step dependency-chain scenario used to first verify multi-step plans (stop `atlas-test-prometheus`, restart `atlas-test-node-exporter`, restart `atlas-test-prometheus` again) — this time confirming "Run this plan now?" and every per-step prompt. All three steps executed for real; `docker ps` afterward showed both containers freshly up (seconds of uptime, not hours), and `atlas history` showed all three `PlanStep`-sourced events with the correct event types and accurate `previous_status` values in each payload.

**Persisting `atlas chat` transcripts.** `chat()` builds a second, separate `transcript` list alongside `messages` — `{"role": "user"/"assistant", "content": <plain string>}` pairs, appended at the same two points the loop already has `user_input`/`reply.text` on hand — and publishes it as one `atlas.chat.transcript_saved` event (`source="AtlasChat"`, `payload={"messages": transcript}`) after the loop ends, only if `transcript` is non-empty (an immediately-exited session doesn't add a no-op row, same rule Proxmox/monitoring change detection already follow). No new table, no new query method — this rides the same `DatabaseListener`-on-`"*"` path every other event already uses, and shows up in `atlas history` for free since it just prints every event's raw JSON payload. **`transcript` deliberately isn't the same list as `messages`.** `messages` is the list actually passed to `agent.converse()`, and both providers mutate it in place — Anthropic's `_run_loop()` appends `{"role": "assistant", "content": response.content}` mid-loop on every tool call, where `response.content` is a list of Anthropic SDK content-block objects, not plain dicts. `KnowledgeStore.save_event()` does a plain `json.dumps(event.payload)`, so publishing `messages` directly would crash on any session where a tool got called — the common case for `atlas chat`, not an edge case. Found by reading `_run_loop()`, not by hitting the crash. Verified against a real local Ollama: a session that genuinely called `get_containers` mid-conversation exited cleanly, and `atlas history` afterward showed the correct two-turn transcript with no serialization error.

**Rich-based CLI conventions.** Every `atlas/cli/main.py` command uses a shared `Console()` and follows the same shape: print a bold header, do the work, print results with `rich` color tags (`[green]✓ ...`, `[yellow]! ...`, `[red]...`), and for commands with a data dependency (`report`, `intelligence`, `analyze`), print a "Run: atlas discover" hint and return early rather than raising when no data exists yet.

**Proxmox guest usage in `atlas trends`.** The last remaining item from resource-usage trending's original scoping — Proxmox guest CPU/memory is now trended alongside host and container metrics, reusing the exact "skip rows lacking the field" mechanism `host_metric_trend()`/`container_metric_trend()` already use for the monitor-vs-discover row split. `atlas/proxmox/trends.py` (new, mirrors `atlas/monitoring/trends.py`, kept as a separate Proxmox-domain module the same way `atlas/proxmox/changes.py` mirrors `atlas/monitoring/changes.py` rather than being folded in) reads `virtualization` (populated by `atlas proxmox scan`, a completely independent save schedule from `atlas monitor`'s `monitoring` field) — "stitching two independently-scheduled time series together," the phrase the original deferral used, turned out to need zero new machinery: the filter-and-skip pattern already there for exactly this reason extends unchanged. Two real unit-normalization decisions, made from what `/cluster/resources` actually provides (already saved in every `atlas proxmox scan` snapshot, no new discovery): `cpu_percent = guest["cpu"] * 100` (percent of one core, the same convention host/container `cpu_percent` already use — not `/ maxcpu`, which would answer "percent of what this guest was allocated" instead); `memory_percent = (guest["mem"] / guest["maxmem"]) * 100`, which is a real, worth-documenting asymmetry with Docker — Proxmox's API gives no host-total comparison the way cAdvisor's separate `container_spec_memory_limit_bytes` query does, so a Proxmox guest's `memory_percent` means what Docker's `memory_percent_of_limit` means (percent of the guest's *own* allocation), not what Docker's host-relative `memory_percent` means, despite sharing the same field name. Guests are matched by vmid (string), never name, same stable-identifier principle `diff_virtualization()` already established. Along the way, fixed a real pre-existing gap the broadened check happened to expose: `atlas trends`'s "no monitoring history found" early-return only ever checked for `monitoring` data, so a host that only ever ran `atlas proxmox scan` (never `atlas monitor`) would incorrectly hit that message even with real guest trend data available — the check now considers `virtualization` too. Verified against the real Proxmox VE host used for every other Proxmox verification in this project: started the real `atlas-test` LXC guest (normally kept stopped), ran several real `atlas proxmox scan`s while it was running, and `atlas trends`/`atlas trends --json` both correctly showed real, non-zero, correctly-normalized CPU/memory trends for it (and a correct all-zero trend for the second real guest, `VM 101`, which stayed stopped throughout) — confirmed via `jq` that the JSON shape (`{"guests": {"100": {"name": "atlas-test", "cpu_percent": {...}, "memory_percent": {...}}}}`) is genuinely valid. Environment restored to its original resting state afterward.

**`atlas web` — a lightweight read-only web view over existing data, the roadmap's last non-blocked open item.** Scoped exactly as the roadmap described it: a view over `atlas report`/`atlas history`/`atlas trends`'s existing `KnowledgeQueries` reads, no new write path, no new automation. Deliberately no new dependency — `atlas/web/server.py` uses stdlib `http.server.ThreadingHTTPServer` + `BaseHTTPRequestHandler`, not Flask/FastAPI, matching this project's existing low-dependency posture (`pyproject.toml`'s `dependencies` list has never included a web framework). `AtlasWebHandler` defines only `do_GET` — there is no `do_POST`/`do_PUT`/`do_DELETE` anywhere in the class, so a write path isn't just avoided by convention, it doesn't exist to be reached; `tests/test_web_server.py::test_only_get_routes_exist_no_write_path` asserts this structurally, not just behaviorally, so a future edit can't silently add one without that test naming it. Three routes: `/` (system/hardware/storage/network/containers/Proxmox guests from `latest_environment()`, plus the latest AI analysis if one exists), `/history` (`recent_events()`, same data `atlas history` prints), `/trends` (see below). `atlas/web/render.py` holds pure HTML-rendering functions (data in, HTML string out, no I/O) - the same "pure function, unit-testable without touching real infra" shape `format_change()`/`_trend_summary()` already established elsewhere in this codebase. All interpolated values go through `html.escape()` (`_esc()`), including container names/labels - a real, if narrow, injection surface since that data ultimately comes from whatever's actually running on the host, not from Atlas itself; confirmed via a dedicated escaping test rather than assumed safe because "it's local."

**`atlas trends`'s JSON-payload logic was extracted into a new pure `build_trends_payload()` (`atlas/reporting/trends.py`), not reimplemented for the web view.** The CLI's `trends()` command previously interleaved "compute the payload" and "print it" in one pass, with `--json` and human-readable output each doing their own partial version of the same computation (the same shape `_trend_summary()` already existed to avoid at the per-metric level, just not yet at the whole-payload level). Pulling the whole `{"host", "containers", "guests"}` payload construction into its own pure function means `atlas trends --json` and `atlas web`'s `/trends` route now call the *identical* code path — they can't compute different numbers from the same underlying history, the same reasoning that already justified `_trend_summary`'s own extraction. `trends()` itself got smaller as a result: it now just calls `build_trends_payload(limit)` once and either prints the JSON or walks the returned dict for human output (a new small `_print_trend_summaries()` helper replaces three near-identical inline print blocks). Confirmed behavior-preserving before adding anything new: ran the full pre-existing test suite against this refactor alone and it passed unchanged, then added `tests/test_reporting_trends.py` as direct coverage of the extracted function.

## Code style notes

The existing codebase (outside `atlas/intelligence/providers/` and `tests/`, which are newer) is written with heavy vertical spacing — each function argument on its own line, a blank line after `def ...():` before the body, blank lines between most statements — and very few docstrings (mostly on classes, not functions). New code should generally match whatever file it's editing rather than importing a different style mid-file.

## Project philosophy (from CONTRIBUTING.md)

- **Local-first**: prefer self-hosted/local solutions where practical (e.g. the Ollama provider option alongside Anthropic).
- **Explainability**: Atlas should be able to explain what it's doing, why, the expected outcome, and any risk — reflected in both code and docs.
- **Safety**: changes affecting real infrastructure should be observable, logged, reversible where possible, and gated behind user approval — Atlas is meant to observe/recommend, not silently act.
